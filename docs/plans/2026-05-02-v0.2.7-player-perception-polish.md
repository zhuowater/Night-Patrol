# v0.2.7 Player Perception & Closed-Playtest Polish Implementation Plan

> **For Hermes:** Use executing-plans for direct in-session execution. Use subagent-driven-development only for independent review/audit tasks. Keep each slice small, verified, and release-oriented.

**Goal:** Use the v0.2.6 senior-player playtest report to move Night Patrol from “mechanically understandable” to “closed-playtest polished”: core counterplay is visually obvious, rewards feel valuable, first-screen/map fit common viewports, and the final victory can be meaningfully reviewed.

**Architecture:** Keep the current React + TypeScript + Vite + Electron structure. Do not add new enemy/card/content systems in v0.2.7. Build on the existing v0.2.6 single-source helpers (`previewAttackChain`, `previewCardEffect`) and add thin UI/presentation helpers where needed. Avoid a broad combat UI rewrite.

**Tech Stack:** React 18, TypeScript, Phaser 3 lazy combat stage, Vite, Electron, Node/tsx validation scripts.

## 0. Baseline and Input Report

**Current baseline:**

- Package version: `night-patrol-soc@0.2.6`
- Latest local release commit: `f639114 docs: finalize v0.2.6 release notes`

**Report judgment to carry into v0.2.7:**

- v0.2.6 is closed-playtest viable, but not yet public-demo polished.
- Biggest risk is not missing systems; it is that players do not *see* the systems already built.
- v0.2.7 should prioritize information architecture, reward feel, viewport fit, and post-run review over content expansion.

## 1. v0.2.7 Product Principle

v0.2.7 should answer one question:

> Can a first-time but experienced card-game player instantly see the important counterplay window, understand why a reward/tool matters, and finish a run with enough recap to give useful feedback?

Priority order:

1. Counterplay visibility: show “condition / current value / ready or missing” instead of burying it in prose.
2. Boss/final-fight readability: phase marks, countdown prominence, and final run summary.
3. Reward value and delight: tool/relic effects and elite rewards should feel like a prize, not a log line.
4. Viewport fit: title, map, bottom CTAs, and card areas must not feel clipped on common laptop/browser viewports.
5. Decision assists: upgrade delta, event result preview, shop/build synergy hints.
6. Release gate: full automated checks, production build, desktop pack, browser smoke with screenshots.

## 2. Non-goals

Do **not** do these in v0.2.7 unless a bug blocks closed playtest:

- Add many new cards, enemies, maps, videos, or audio tracks.
- Redesign the full combat screen layout.
- Add multi-enemy targeting.
- Add save/load meta-progression.
- Start public marketing/Steam work.
- Replace Phaser combat stage or audio architecture.

### Task 1: Add Structured Counterplay Readiness Data

**Objective:** Convert counterplay prose into machine-readable readiness rows so UI can display clear `已满足 / 还差 N` chips.

```ts
export type CounterplayReadiness = {
  id: "c2" | "credential" | "ransomware" | "lateral" | "generic";
  label: string;
  requirement: string;
  current: string;
  ready: boolean;
  missing?: string;
  tone: "ready" | "warning" | "info";
};

export type AttackChainPreview = {
  riskForecast: string[];
  counterplayWindows: string[];
```

**Steps:**

2. Extend `previewAttackChain(state)` to populate rows for chains already handled in v0.2.6:

4. Add assertions in `scripts/check-engine-scenarios.ts` for at least:
   - C2 not ready with zero IOC.
   - C2 ready with one IOC.
   - Ransomware ready with two compute.
   - Credential row includes noise/current info.

### Task 3: Add Card-Level “Solves Current Threat” Hint

**Objective:** Highlight cards that directly answer the current intent or attack-chain window.

**Files:**

**Target helper:**

```ts
export function cardThreatHint(
  card: CardInstance,
  context: { combat: CombatState; player: PlayerState }
): null | {
  label: string;
  tone: "attack" | "defense" | "counter" | "resource";
};
```

**Rules (keep simple):**

- If enemy intends attack and card grants block: `补足防护窗口`.
- If chain includes `C2` and card applies IOC: `可拦截 C2 信标`.
- If chain includes `勒索` and card grants compute/incense: `补算力取消倒计时`.
- If chain includes `凭据` or `横向移动` and card applies weak/降权: `可压制凭据/横移`.
- If enemy has IOC and card consumes/benefits from IOC: `兑现 IOC 爆发`.

**Steps:**

1. Implement `cardThreatHint` using card IDs and/or card text; do not build a simulator.
2. Add an optional `threatHint` prop to `GameCard`.
3. In `CombatScreen`, compute hint for each hand card with current `combat` and `player`.
4. Render a small ribbon on the card when `threatHint` exists.
5. Add CSS for `.card-threat-hint` and tone variants.
6. Ensure disabled/unplayable cards do not look recommended even if they match a rule; either hide hint or add muted styling.

## 8. Known Risks and Guardrails

- **Risk:** Combat panel becomes even denser.  
  **Guardrail:** readiness chips should replace mental parsing, not add long copy. Keep each chip one line + small detail.

- **Risk:** Hint rules become a fake AI advisor.  
  **Guardrail:** only deterministic, obvious rules; no hidden strategy engine.

- **Risk:** Viewport CSS breaks existing visual identity.  
  **Guardrail:** use responsive compaction and internal scroll, not a redesign.

- **Risk:** Victory summary needs data not currently tracked.  
  **Guardrail:** derive from existing `GameState`; do not add run-history persistence in v0.2.7.

- **Risk:** Manual Boss smoke is slow.  
  **Guardrail:** keep deterministic script coverage for Boss preview, and use browser route if feasible; do not ship dev-only shortcuts.
